# Canonical OpenThread deltas for OTNS porting

These patches capture the OpenThread source generated by the repository's
current patchers when replayed against the clean ESP-IDF 5.5.4 package tree in
`testing/.platformio-core/stock`.

They are audit artifacts for the OTNS port. They do not replace the PlatformIO
patchers used by ESPHome builds.

## Patch order

Apply from the directory containing `src/core`:

```bash
patch -p1 < preferred-parent-functional.patch
patch -p1 < preferred-parent-diagnostics.patch
patch -p1 < fast-unicast-parent-response.patch  # fast-response routers only
```

The preferred-parent patches affect:

- `src/core/thread/mle.hpp`;
- `src/core/thread/mle.cpp`;
- `src/core/thread/mle_ftd.cpp`;
- `src/core/api/thread_api.cpp`.

The fast-response patch affects only `src/core/thread/mle_ftd.cpp` and must be
applied after the preferred-parent functional patch because both change the
provisional child timeout area.

## Generation and verification

1. Copy the relevant files from the isolated stock OpenThread package tree.
2. Run
   `components/thread_preferred_parent/apply-openthread-selected-parent-hook.py`
   against the copy.
3. Repeat with independently removable diagnostic functions disabled.
4. Diff stock to functional for the functional patch.
5. Diff functional to the ordinary full patcher output for diagnostics.
6. Run the fast-response patcher against the full preferred-parent tree.
7. Diff the full preferred-parent tree to the fast-response tree.

The full generated preferred-parent tree matched the existing isolated `mcast`,
`ucast`, and `ucast_fastpr` build trees byte-for-byte for the four audited
files. The `mcast` and `ucast` OpenThread source trees are identical; ESPHome
configuration selects their runtime behavior.

The patches were also applied in order to another clean stock copy. The result
matched the generated preferred-parent and fast-response trees byte-for-byte.

## Known generated-source issue

The patcher declares `mPreferredDiscoveryParentCandidate` and
`mHasPreferredDiscoveryParentCandidate`, and its continuation method can use
that snapshot. In the audited ESP-IDF 5.5.4 source layout:

- the snapshot transformation reports `missing` because its pattern does not
  match;
- the snapshot candidate is never initialized or populated;
- the boolean is not initialized in the `Attacher` constructor;
- immediate unicast discovery explicitly sets the boolean to `false` before
  use, but ordinary multicast discovery does not;
- direct continuation normally succeeds through the live `mParentCandidate`
  fallback, not through the intended snapshot.

This is part of the observed generated source and remains represented in the
canonical patches. The OTNS port must not copy the undefined state. It must
initialize its state and either implement a valid snapshot or deliberately use
a validated live candidate.
